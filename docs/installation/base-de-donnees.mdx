# Modèles et structure de la base de données SantéSN

> Présentation des modèles de données inférés du comportement de SantéSN : assurés, ordonnances, prises en charge et journal d'audit immuable.

SantéSN s'appuie sur une base de données PostgreSQL dont la structure reflète les acteurs et les processus métier de la plateforme : gestion des assurés, des ordonnances sécurisées, des prises en charge et des journaux d'activité. Cette page décrit les principaux modèles (tables), leurs champs estimés et les relations qui les unissent.

<Warning>
  **Les modèles décrits sur cette page sont entièrement déduits du comportement observable de la plateforme.** Aucun fichier de schéma public, aucun diagramme ERD officiel et aucun code source n'ont été consultés pour rédiger cette documentation. La structure réelle des tables peut différer. Référez-vous toujours aux fichiers de migration Django (`*/migrations/`) présents dans le dépôt comme seule source de vérité.
</Warning>

<Info>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Les noms de modèles, de champs et de choix (`choices`) présentés ci-dessous sont des estimations raisonnables basées sur les fonctionnalités visibles de SantéSN.
</Info>

## Description des modèles

### Utilisateur

Le modèle `Utilisateur` est le modèle d'authentification personnalisé de SantéSN. Il remplace le modèle `User` par défaut de Django.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Les noms de champs et leurs types sont estimés d'après les fonctionnalités observables (connexion par email, rôles multiples, verrouillage de compte).
</Note>

| Champ         | Type          | Description estimée                                                       |
| ------------- | ------------- | ------------------------------------------------------------------------- |
| `id`          | UUID / int    | Identifiant unique                                                        |
| `email`       | EmailField    | Identifiant de connexion (unique). Remplace le `username` standard Django |
| `password`    | CharField     | Hash PBKDF2 avec sel cryptographique individuel                           |
| `role`        | CharField     | Rôle de l'utilisateur : `assuré`, `médecin`, `pharmacien`, `admin`, `ipm` |
| `is_active`   | BooleanField  | Compte actif ou verrouillé (après tentatives de connexion échouées)       |
| `date_joined` | DateTimeField | Date de création du compte                                                |

<Info>
  Il n'existe pas d'inscription publique sur SantéSN. Tous les comptes sont créés par un administrateur institutionnel depuis le tableau de bord d'administration.
</Info>

### Profil / Assuré

Le modèle `Assuré` étend le profil de l'utilisateur pour les patients couverts par une IPM ou une compagnie d'assurance.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Les champs listés sont inférés des fonctionnalités de tiers payant et de gestion de couverture observées.
</Note>

| Champ             | Type         | Description estimée                          |
| ----------------- | ------------ | -------------------------------------------- |
| `utilisateur`     | OneToOne     | Lien vers `Utilisateur`                      |
| `matricule_ipm`   | CharField    | Numéro d'immatriculation IPM                 |
| `taux_couverture` | DecimalField | Taux de prise en charge par l'assurance (%)  |
| `ipm`             | ForeignKey   | Lien vers l'organisation `Prestataire` (IPM) |
| `date_adhesion`   | DateField    | Date d'adhésion au régime de couverture      |

***

### AyantDroit

Le modèle `AyantDroit` représente les personnes à charge (conjoint, enfants) rattachées au compte d'un assuré principal.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. L'existence de ce modèle est inférée de la fonctionnalité de gestion des dépendants visible dans l'interface.
</Note>

| Champ            | Type       | Description estimée                                 |
| ---------------- | ---------- | --------------------------------------------------- |
| `assure`         | ForeignKey | Lien vers l'assuré principal (`Assuré`)             |
| `nom`            | CharField  | Nom de l'ayant droit                                |
| `prenom`         | CharField  | Prénom de l'ayant droit                             |
| `lien`           | CharField  | Lien de parenté : `conjoint`, `enfant`              |
| `date_naissance` | DateField  | Date de naissance (pour vérification d'éligibilité) |

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Les champs sont inférés des fonctionnalités de prescription et de gestion des rendez-vous accessibles au rôle `médecin`.
</Note>

| Champ          | Type       | Description estimée                                  |
| -------------- | ---------- | ---------------------------------------------------- |
| `utilisateur`  | OneToOne   | Lien vers `Utilisateur`                              |
| `numero_ordre` | CharField  | Numéro d'inscription à l'Ordre des médecins          |
| `specialite`   | CharField  | Spécialité médicale                                  |
| `prestataire`  | ForeignKey | Établissement de santé auquel le médecin est attaché |

### Pharmacien

Le modèle `Pharmacien` étend le profil utilisateur pour les pharmaciens habilités à vérifier et délivrer les ordonnances.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Les champs sont inférés des fonctionnalités de vérification et de délivrance d'ordonnances accessibles au rôle `pharmacien`.
</Note>

| Champ          | Type       | Description estimée                             |
| -------------- | ---------- | ----------------------------------------------- |
| `utilisateur`  | OneToOne   | Lien vers `Utilisateur`                         |

| `prestataire`  | ForeignKey | Pharmacie à laquelle le pharmacien est rattaché |

### Prestataire

Le modèle `Prestataire` représente les structures de santé partenaires : cliniques, hôpitaux, pharmacies, ou les IPM elles-mêmes.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. L'existence de ce modèle est inférée des relations multi-acteurs observées entre médecins, pharmaciens et assureurs.
</Note>

| Champ       | Type         | Description estimée                                   |
| ----------- | ------------ | ----------------------------------------------------- |
| `nom`       | CharField    | Dénomination de l'établissement                       |
| `type`      | CharField    | Type : `clinique`, `hôpital`, `pharmacie`, `ipm`      |
| `adresse`   | TextField    | Adresse physique                                      |
| `telephone` | CharField    | Numéro de contact                                     |
| `actif`     | BooleanField | Indique si le prestataire est actif sur la plateforme |

### RendezVous

Le modèle `RendezVous` gère les prises de rendez-vous entre assurés (ou ayants droit) et médecins.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Les champs et statuts sont inférés de la fonctionnalité de prise de rendez-vous observable dans le tableau de bord.
</Note>

| Champ         | Type          | Description estimée                                          |
| ------------- | ------------- | ------------------------------------------------------------ |
| `assure`      | ForeignKey    | Patient concerné (`Assuré` ou `AyantDroit`)                  |
| `medecin`     | ForeignKey    | Médecin consulté                                             |
| `prestataire` | ForeignKey    | Établissement où se déroule le rendez-vous                   |
| `date_heure`  | DateTimeField | Date et heure du rendez-vous                                 |
| `statut`      | CharField     | État estimé : `en_attente`, `confirmé`, `annulé`, `effectué` |
| `motif`       | TextField     | Motif de la consultation (facultatif)                        |

***

### Consultation

Le modèle `Consultation` enregistre l'acte médical réalisé à l'issue d'un rendez-vous.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. L'isolement du champ `diagnostic` est inféré de la politique de confidentialité et du contrôle d'accès par rôle observable.
</Note>

| Champ        | Type          | Description estimée                                              |
| ------------ | ------------- | ---------------------------------------------------------------- |
| `rendezvous` | OneToOne      | Rendez-vous associé (`RendezVous`)                               |
| `medecin`    | ForeignKey    | Médecin ayant réalisé la consultation                            |
| `patient`    | ForeignKey    | Patient concerné                                                 |
| `diagnostic` | TextField     | Diagnostic médical (**accès restreint** aux médecins uniquement) |
| `traitement` | TextField     | Description du traitement préconisé                              |
| `date`       | DateTimeField | Date et heure de la consultation                                 |

<Warning>
  Le champ `diagnostic` est soumis à une isolation stricte par rôle (RBAC). Les administrateurs de la plateforme n'ont pas accès aux données médicales telles que les diagnostics, conformément à la politique de confidentialité de SantéSN et à la loi n° 2008-12 sur la protection des données personnelles au Sénégal.
</Warning>

***

### Ordonnance

Le modèle `Ordonnance` représente une prescription médicale sécurisée, identifiée par un code unique et protégée par un QR Code infalsifiable.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Le format `RX-XXXXXXXXXX`, la validité de 90 jours et le verrouillage anti-double-dispensation sont inférés du comportement observable de la plateforme.
</Note>

| Champ             | Type          | Description estimée                                                   |
| ----------------- | ------------- | --------------------------------------------------------------------- |
| `code`            | CharField     | Identifiant unique au format `RX-XXXXXXXXXX` (généré automatiquement) |
| `qr_code`         | ImageField    | QR Code généré à partir du code `RX`                                  |
| `consultation`    | ForeignKey    | Consultation à l'origine de l'ordonnance                              |
| `medecin`         | ForeignKey    | Médecin prescripteur                                                  |
| `patient`         | ForeignKey    | Patient bénéficiaire                                                  |
| `statut`          | CharField     | État estimé : `active`, `délivrée`, `expirée`                         |
| `date_creation`   | DateTimeField | Date de création de l'ordonnance                                      |
| `date_expiration` | DateField     | Date limite de validité (90 jours après création par défaut)          |

<Note>
  Par défaut, toute ordonnance créée sur SantéSN expire **90 jours** après sa date de création. Une ordonnance au statut `délivrée` est verrouillée : elle ne peut plus être délivrée une seconde fois, ce qui empêche toute double dispensation frauduleuse.
</Note>

<Note>

| Champ        | Type         | Description estimée                                      |
| ------------ | ------------ | -------------------------------------------------------- |
| `ordonnance` | ForeignKey   | Ordonnance parente                                       |

### PriseEnCharge

Le modèle `PriseEnCharge` enregistre l'événement de remboursement associé à la délivrance d'une ordonnance, en calculant automatiquement la part assurance et la part patient.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Les champs de calcul automatique du tiers payant sont inférés de la fonctionnalité de prise en charge automatique observable dans l'interface.
</Note>

| Champ            | Type          | Description estimée                            |
| ---------------- | ------------- | ---------------------------------------------- |
| `ordonnance`     | OneToOne      | Ordonnance concernée                           |
| `assure`         | ForeignKey    | Assuré (ou ayant droit) bénéficiaire           |
| `ipm`            | ForeignKey    | IPM ou compagnie d'assurance prenant en charge |
| `montant_total`  | DecimalField  | Montant total de l'acte                        |
| `part_assurance` | DecimalField  | Montant pris en charge par l'assurance         |
| `part_patient`   | DecimalField  | Montant restant à la charge du patient         |
| `date`           | DateTimeField | Date de la prise en charge                     |

***

### JournalActivite

Le modèle `JournalActivite` est le journal d'audit immuable de la plateforme. Il enregistre toutes les opérations sensibles effectuées par les utilisateurs.

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. L'existence d'un journal d'activité immuable et son caractère *append-only* sont inférés des garanties d'audit décrites dans la politique de confidentialité et des comportements observés lors de la navigation.
</Note>

| Champ         | Type                  | Description estimée                                                    |
| ------------- | --------------------- | ---------------------------------------------------------------------- |
| `utilisateur` | ForeignKey            | Utilisateur ayant réalisé l'action                                     |
| `action`      | CharField             | Type d'action (ex. : `connexion`, `création_ordonnance`, `délivrance`) |
| `description` | TextField             | Détail de l'opération                                                  |
| `adresse_ip`  | GenericIPAddressField | Adresse IP de l'utilisateur au moment de l'action                      |
| `horodatage`  | DateTimeField         | Date et heure exactes de l'action (auto-générée)                       |
| `objet_type`  | CharField             | Type de l'objet concerné (ex. : `Ordonnance`, `RendezVous`)            |
| `objet_id`    | CharField             | Identifiant de l'objet concerné                                        |

<Warning>
  La table `JournalActivite` est **en ajout seul** (*append-only*). Aucune opération de mise à jour (`UPDATE`) ou de suppression (`DELETE`) n'est autorisée sur ces enregistrements. Cette règle garantit l'intégrité et la non-répudiation du journal d'audit, conformément aux exigences de la CDP Sénégal (loi n° 2008-12).
</Warning>

```
Médecin     ──(N:1)──► Prestataire (clinique/hôpital)
Pharmacien  ──(N:1)──► Prestataire (pharmacie)

RendezVous  ──(N:1)──► Assuré
RendezVous  ──(N:1)──► Médecin
RendezVous  ──(N:1)──► Prestataire

Consultation──(1:1)──► RendezVous

Ordonnance  ──(1:N)──► LigneOrdonnance

```

<Note>
  Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source. Les relations représentées ici sont des estimations basées sur les flux fonctionnels observés et les bonnes pratiques Django standard.
</Note>

<Accordion title="Pourquoi Utilisateur est-il séparé des profils Médecin / Assuré ?">
  Cette architecture suit le principe de séparation des responsabilités. Le modèle `Utilisateur` gère exclusivement l'authentification (email, mot de passe, rôle, statut actif). Les modèles `Assuré`, `Médecin` et `Pharmacien` portent les données métier propres à chaque rôle. Cette séparation facilite l'isolation des données sensibles (diagnostics médicaux) des données d'accès et d'administration.
</Accordion>

<Accordion title="Comment les ayants droit accèdent-ils aux services ?">
  Les `AyantDroit` n'ont pas de compte `Utilisateur` propre. Ils sont rattachés au compte de leur assuré principal. Lorsqu'un assuré réserve un rendez-vous ou génère une prise en charge pour un ayant droit, le champ `assure` du modèle concerné peut pointer soit vers l'assuré principal, soit vers l'un de ses ayants droit selon l'implémentation retenue.

  <Note>
    Ce point est déduit du comportement de la plateforme et n'a pas été vérifié dans le code source.
  </Note>
</Accordion>
