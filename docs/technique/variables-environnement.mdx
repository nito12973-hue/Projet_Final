# Variables d'environnement de configuration SantéSN

> Liste des variables d'environnement requises pour déployer SantéSN en local ou en production sur Vercel, avec exemples de valeurs et bonnes pratiques.

SantéSN utilise des variables d'environnement pour séparer la configuration sensible (clés secrètes, identifiants de base de données) du code source. Ces variables ne doivent jamais être versionnées dans le dépôt Git.

## Variables requises

<ParamField path="SECRET_KEY" type="string" required>
  Clé secrète Django utilisée pour la signature cryptographique des sessions, des tokens CSRF et des URLs temporaires. Doit être longue (50+ caractères), aléatoire et unique par environnement.

  **Exemple :** `django-insecure-abc123...` *(remplacer par une valeur générée aléatoirement en production)*
</ParamField>

<ParamField path="DEBUG" type="boolean" required>
  Active ou désactive le mode debug de Django. En mode debug, les erreurs affichent une trace complète dans le navigateur — à ne jamais activer en production.

  **Valeur en développement :** `True`\
  **Valeur en production :** `False`
</ParamField>

<ParamField path="ALLOWED_HOSTS" type="string" required>
  Liste des noms de domaine autorisés à servir l'application Django, séparés par des virgules. Protège contre les attaques par injection d'en-tête `Host`.

  **Exemple :** `127.0.0.1,.vercel.app,projet-final-bice.vercel.app`
</ParamField>

<ParamField path="DATABASE_URL" type="string">
  URL de connexion complète à la base de données PostgreSQL, au format standard. Utilisée comme alternative aux variables `DB_*` individuelles.

  **Exemple :** `postgres://santesn:motdepasse@localhost:5432/santesn_db`
</ParamField>

<ParamField path="DB_NAME" type="string" required>
  Nom de la base de données PostgreSQL.

  **Exemple :** `santesn_db`
</ParamField>

<ParamField path="DB_USER" type="string" required>
  Nom d'utilisateur PostgreSQL disposant des droits de lecture/écriture sur `DB_NAME`.

  **Exemple :** `santesn`
</ParamField>

<ParamField path="DB_PASSWORD" type="string" required>
  Mot de passe de l'utilisateur PostgreSQL. Ne jamais utiliser un mot de passe vide en production.

  **Exemple :** `***` *(valeur confidentielle)*
</ParamField>

<ParamField path="DB_HOST" type="string" required>
  Nom d'hôte ou adresse IP du serveur PostgreSQL.

  **Exemple :** `localhost` *(développement)* ou l'adresse de votre serveur managé en production
</ParamField>

<ParamField path="DB_PORT" type="string" required>
  Port d'écoute du serveur PostgreSQL. La valeur par défaut de PostgreSQL est `5432`.

  **Exemple :** `5432`
</ParamField>

## Fichier `.env.example`

Utilisez ce fichier comme point de départ pour votre configuration locale. Copiez-le en `.env`, puis renseignez les valeurs réelles.

```bash theme={null}
# .env.example — SantéSN
# Copiez ce fichier en .env et renseignez toutes les valeurs avant de lancer l'application.
# Ne commitez JAMAIS le fichier .env dans votre dépôt Git.

# Django
SECRET_KEY=remplacez-par-une-cle-secrete-aleatoire-de-50-caracteres-minimum
DEBUG=False
ALLOWED_HOSTS=127.0.0.1,.vercel.app

# Base de données PostgreSQL
# Option 1 : URL complète
DATABASE_URL=postgres://DB_USER:DB_PASSWORD@DB_HOST:DB_PORT/DB_NAME

# Option 2 : variables individuelles
DB_NAME=santesn_db
DB_USER=santesn
DB_PASSWORD=
DB_HOST=localhost
DB_PORT=5432
```

<Warning>
  Ne commitez **jamais** votre fichier `.env` dans Git. Ajoutez-le immédiatement à votre `.gitignore` :

  ```bash theme={null}
  echo ".env" >> .gitignore
  ```

  Une fuite de `SECRET_KEY` ou des identifiants PostgreSQL en dépôt public peut entraîner une compromission complète de la plateforme et des données de santé qu'elle contient.
</Warning>

## Configuration sur Vercel

<Note>
  Lors du déploiement sur Vercel, les variables d'environnement ne sont **pas** lues depuis un fichier `.env`. Vous devez les saisir directement dans l'interface Vercel :

  1. Ouvrez votre projet sur [vercel.com](https://vercel.com)
  2. Accédez à **Settings** → **Environment Variables**
  3. Ajoutez chaque variable avec sa valeur pour les environnements **Production**, **Preview** et **Development** selon vos besoins
  4. Redéployez le projet pour que les nouvelles variables soient prises en compte
</Note>

## Génération d'une `SECRET_KEY` sécurisée

Pour générer une clé secrète Django robuste en ligne de commande :

```bash theme={null}
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Ou avec Python standard, sans Django installé :

```python theme={null}
import secrets
print(secrets.token_urlsafe(50))
```

<Tip>
  Utilisez une `SECRET_KEY` différente pour chaque environnement (développement, staging, production). Si une clé est compromise, vous pouvez la remplacer sans affecter les autres environnements — toutes les sessions actives seront invalidées, ce qui est le comportement souhaité en cas d'incident de sécurité.
</Tip>
