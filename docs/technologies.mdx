# Pile technique de SantéSN : Django, Vercel et sécurité

> Inventaire des technologies de SantéSN : Django, Vercel, PostgreSQL, QR Code, TLS 1.3, PBKDF2 et conformité CDP Sénégal Loi n°2008-12.

SantéSN est construit sur une pile technologique éprouvée, délibérément centrée sur Django pour la robustesse du backend et la rapidité du développement métier. Le déploiement sur Vercel en runtime Python serverless garantit la disponibilité sans infrastructure à administrer. Cette page recense chaque technologie utilisée, son rôle dans la plateforme et, le cas échéant, précise si l'information est **confirmée** par la politique de confidentialité et les en-têtes HTTP du site, ou **déduite** des pratiques standard de l'écosystème.

<Info>
  Les entrées marquées **✅ Confirmé** sont directement attestées par la politique de confidentialité publiée sur la plateforme ou par inspection des en-têtes HTTP. Les entrées marquées **🔍 Déduit** correspondent aux choix techniques standards de l'écosystème Django/Vercel et sont très probablement exacts, mais non explicitement documentés dans les sources publiques du projet.
</Info>

## Authentification et sécurité des mots de passe

<CardGroup cols={2}>
  <Card title="Sessions Django" icon="clock" href="/technique/securite">
    **✅ Confirmé** — L'authentification repose sur les sessions natives de Django. La durée de session est de **8 heures**. Le cookie `sessionid` est configuré avec les attributs `HttpOnly` et `SameSite=Lax` pour limiter les vecteurs d'attaque XSS et CSRF.
  </Card>

  <Card title="PBKDF2 + sel cryptographique" icon="key" href="/fonctionnalites/authentification">
    **✅ Confirmé** — Les mots de passe sont hachés avec l'algorithme PBKDF2 (Password-Based Key Derivation Function 2) associé à un sel cryptographique individuel par compte. Aucun mot de passe n'est stocké en clair.
  </Card>
</CardGroup>

## Sécurité applicative

| Mécanisme                  | Statut     | Description                                                                                                               |
| -------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------- |
| **HTTPS / TLS 1.3**        | ✅ Confirmé | Toutes les communications sont chiffrées en transit. TLS 1.3 est la version minimale acceptée.                            |
| **HSTS**                   | ✅ Confirmé | L'en-tête `Strict-Transport-Security` force le navigateur à n'utiliser HTTPS que pour toutes les requêtes ultérieures.    |
| **X-Content-Type-Options** | ✅ Confirmé | En-tête `nosniff` — empêche le navigateur de deviner le type MIME des réponses.                                           |
| **X-Frame-Options DENY**   | ✅ Confirmé | Bloque l'intégration de la plateforme dans une `<iframe>`, protégeant contre le clickjacking.                             |
| **Protection CSRF**        | ✅ Confirmé | Cookie `csrftoken` requis sur tous les formulaires POST via le middleware CSRF natif de Django.                           |
| **Anti-force-brute**       | 🔍 Déduit  | Verrouillage du compte après plusieurs tentatives de connexion échouées. Le seuil exact n'est pas documenté publiquement. |

## Gestion des cookies

Les deux cookies suivants sont déposés lors de l'authentification :

<CardGroup cols={2}>
  <Card title="sessionid" icon="cookie" href="/technique/securite">
    **✅ Confirmé** — Cookie de session. Durée de vie : **8 heures**. Attributs : `HttpOnly` (inaccessible au JavaScript de la page), `SameSite=Lax` (protection contre les attaques CSRF cross-site). Non accessible aux scripts tiers.
  </Card>

  <Card title="csrftoken" icon="shield" href="/technique/securite">
    **✅ Confirmé** — Jeton de protection CSRF. Lisible par le JavaScript first-party pour l'inclure dans les requêtes POST. Renouvelé à chaque session. Obligatoire pour toute soumission de formulaire.
  </Card>
</CardGroup>

## Génération de QR Code

<CardGroup cols={2}>
  <Card title="QR Code d'ordonnance" icon="qrcode" href="/fonctionnalites/ordonnances">
    **✅ Confirmé** — Chaque ordonnance reçoit un QR Code unique lors de sa création par le médecin. Ce QR Code encode l'identifiant `RX-XXXXXXXXXX` et permet au pharmacien de vérifier l'authenticité et la validité de l'ordonnance en temps réel. La bibliothèque Python exacte utilisée pour la génération n'est pas documentée publiquement.
  </Card>

  <Card title="Verrou anti-double-délivrance" icon="lock" href="/fonctionnalites/ordonnances">
    **✅ Confirmé** — Une fois qu'un pharmacien a confirmé la délivrance d'une ordonnance, le système active un verrou qui empêche tout nouveau scan de conduire à une seconde délivrance. Ce mécanisme est géré en base de données.
  </Card>
</CardGroup>

## Conformité réglementaire

<CardGroup cols={2}>
  <Card title="CDP Sénégal — Loi n°2008-12" icon="scale-balanced" href="https://projet-final-bice.vercel.app/politique-confidentialite/">

La politique de confidentialité publiée sur la plateforme détaille les droits des utilisateurs.

</CardGroup>
